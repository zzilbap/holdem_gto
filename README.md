# 홀덤 GTO 솔버

초보자가 쓸 수 있는 텍사스 홀덤 GTO 솔버.

계산은 GTO Wizard와 같은 방식(CFR)으로 하되, **인터페이스는 포커를 막 시작한 사람 기준**으로 만든다.
Wizard는 정확하지만 "BTN vs BB SRP" 같은 표기와 13×13 매트릭스를 먼저 들이밀어서 진입 장벽이 높다.
여기서는 상황을 문장으로 먼저 보여주고, 결론을 먼저 말하고, 매트릭스는 심화 뷰로 접어둔다.

## 엔진이 맞는지 어떻게 아는가

정답이 이미 알려진 것들로만 검증한다. 테스트 62개 중 핵심:

- **핸드 평가기** — 5장 조합 2,598,960개를 전수 분류했을 때 족보 빈도가 교과서 값과 정확히 일치하고,
  서로 다른 핸드 값의 개수가 정확히 **7462개**다.
- **에퀴티 표** — 콤보를 전부 돌려 따로 계산한 169-추상화 평균과 0.5%p 이내로 일치.
- **CFR 엔진** — 내시 균형이 공표된 숏스택 푸시/폴드를 풀렸을 때 **SB 푸시 59.3%** (알려진 값 59%).
  두 플레이어 EV 합이 **-0.0000bb**(제로섬), 폴드하는 패의 EV가 **정확히 -0.5bb**(SB 블라인드 손실).

## 구조

```
packages/
  poker-core/     카드·핸드평가·레인지·에퀴티. 순수 TS, 의존성 0.
  solver/         CFR 엔진. poker-core만 의존.
  solver-client/  솔브 실행 추상화 (Worker → 나중에 서버 API).
apps/
  web/            Next.js. UI만. 포커 로직 0줄.
```

의존 방향은 `web → solver-client → solver → poker-core` 한쪽으로만 흐른다.
그래서 엔진은 브라우저든 Node 서버든 그대로 돌아간다.

설계 결정과 그 근거는 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)에 있다.
특히 "왜 6맥스 전체 트리를 한 번에 풀지 않는가"는 실측 데이터와 함께 적어뒀다.

## 개발

```bash
npm install
npm test          # 전체 테스트
npm run typecheck
```

정적 사이트로 시작하지만, 나중에 로그인·저장·서버 솔브가 붙어도 갈아엎지 않도록
바뀔 지점(`SolverTransport` / `Repository` / `AuthProvider`)을 인터페이스로 격리해뒀다.
