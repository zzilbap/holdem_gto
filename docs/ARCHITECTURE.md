# 아키텍처

## 목표

1. **지금**: 백엔드 없이 정적 배포. 모든 계산은 브라우저에서.
2. **나중**: 로그인 / 저장 / 결제 / 서버 솔브가 붙어도 **UI와 엔진 코드를 갈아엎지 않는다.**

이 두 가지를 동시에 만족시키려면 "지금 안 쓰는 것"을 미리 만드는 게 아니라,
**나중에 바뀔 지점을 인터페이스로 격리**해 두면 된다. 아래 3개가 그 지점이다.

| 나중에 바뀌는 것 | 격리 인터페이스 | 현재 구현 | 미래 구현 |
|---|---|---|---|
| 솔브를 어디서 돌리나 | `SolverTransport` | Web Worker | POST /api/solve (서버 CFR) |
| 데이터를 어디에 두나 | `Repository<T>` | localStorage | REST/DB |
| 사용자가 누구인가 | `AuthProvider` | 익명 고정 | OAuth / 세션 |

조회 기록(사용자가 솔버에 넣었던 스팟들을 나중에 다시 보는 기능)도 `Repository`를 탄다.
지금은 localStorage에 쌓이고, 계정이 생기면 같은 인터페이스로 서버에 쌓인다.
기록이 기기에 묶이지 않으려면 이 격리가 처음부터 있어야 한다.

UI는 이 인터페이스만 알고 구현체는 모른다. 서비스 전환 = 구현체 3개 교체.

## 패키지 구조

```
packages/
  poker-core/     카드·핸드평가·레인지·에퀴티. 순수 TS, 의존성 0.
  solver/         CFR 엔진 (프리플롭 / 플롭). poker-core만 의존.
  solver-client/  솔브 실행 추상화. SolverTransport 인터페이스 + Worker 구현.
apps/
  web/            Next.js. UI만. 포커 로직 0줄.
```

**의존 방향은 한쪽으로만 흐른다.** `web → solver-client → solver → poker-core`
역방향 import 금지. 그래서 `solver`는 브라우저든 Node 서버든 그대로 돌아간다 —
서버 솔브를 붙일 때 엔진을 다시 짤 필요가 없는 이유가 이것이다.

## 왜 엔진이 TypeScript인가

플롭 CFR은 무거워서 보통 Rust→WASM으로 짠다. 지금 TS로 가는 이유:

- Rust 툴체인이 이 환경에 없고, 도입하면 빌드·배포가 복잡해진다.
- 성능이 필요한 루프는 전부 `Float32Array` 위에서 돈다. TS라도 이 형태면 WASM 대비 3~5배 차이 안에 들어온다.
- **엔진은 `Solver` 인터페이스 뒤에 있다.** 나중에 Rust/WASM으로 다시 짜도
  `WasmSolver implements Solver`를 추가하고 주입만 바꾸면 된다. UI는 모른다.

즉 TS 선택은 되돌릴 수 있는 결정이고, 지금 속도를 위해 그렇게 한다.

## 프리플롭을 "전체 트리 한 번에"가 아니라 스팟 단위로 푸는 이유

6맥스 100bb 프리플롭 트리를 실제로 만들어서 재봤다.

| 설정 | 노드 | 전략 슬롯 | 메모리 |
|---|---|---|---|
| 림프 허용 | 369,953 | 6250만 | 477MB |
| 림프 금지 | 72,798 | 1230만 | 94MB |

메모리는 어떻게든 되지만 **속도가 안 된다.** 터미널 노드가 3.9만 개이고
그중 쇼다운/플롭행 노드는 EV를 구할 때마다 169×169 에퀴티 행렬곱(28,561 MAC)이 필요하다.
CFR 한 바퀴에 약 10억 연산 → 브라우저에서 수렴까지 수십 분. 쓸 수 없다.

그래서 **스팟 분할**로 간다. 각 스팟을 2인 게임으로 떼어내 정확히 풀고,
서로 의존하는 레인지는 반복해서 수렴시킨다 (fictitious play).

```
vs 4벳  ──┐
vs 3벳  ──┼── 뒤에서부터 풀고, 나온 레인지를 앞 스팟에 먹인다.
vs RFI  ──┤   앞이 바뀌면 뒤도 다시 푼다. 수렴할 때까지 반복.
RFI     ──┘
```

2인 스팟 트리는 노드 수십 개라 CFR 1000회가 1초 미만이다.
브라우저에서 스택·사이즈를 바꿔가며 실시간으로 다시 풀 수 있다는 뜻이고,
이건 프리솔브 DB만 보여주는 Wizard보다 오히려 나은 점이 된다.

**대가**: 콜드콜이 낀 멀티웨이 팟을 정확히 풀지 않는다. 오픈의 EV를 구할 때
"뒤 사람들 중 첫 논폴드 액션자"까지만 보고, 그 뒤에 또 누가 끼는 경우를 무시한다.
실무 오차는 작지만 0은 아니다. 정확한 멀티웨이가 필요해지면 서버 프리솔브로 옮기면 되고,
그때도 `Solver` 인터페이스는 그대로다.

## 지금 남아 있는 정확도 한계

프리플롭 CFR 자체는 검증됐다 (푸시/폴드 내시 균형 재현, 제로섬 오차 0).
남은 오차는 전부 **에퀴티 실현율(R) 근사**에서 온다.

콜하고 플롭에 가는 노드의 가치를 알려면 포스트플롭을 풀어야 하는데,
프리플롭 CFR 안에서는 그럴 수 없다. 그래서 `플롭 이후 몫 ≈ 에퀴티 × R`로 근사한다.
R은 포지션, 핸드 모양, SPR, 그리고 **상대 레인지의 폭**으로 정한다.

현재 결과와 실제 해법의 차이:

| | 우리 | 통용되는 값 |
|---|---|---|
| UTG RFI | 21.0% | ~16% |
| HJ RFI | 24.3% | ~20% |
| CO RFI | 31.7% | ~27% |
| BTN RFI | 50.5% | ~45% |
| SB RFI | 39.5% | ~40% |
| BB가 UTG 오픈에 폴드 | 44.6% | ~57% |

**전반적으로 조금씩 느슨하다** — 실제보다 넓게 참여한다. R을 후하게 잡고 있다는 뜻이다.
파라미터를 더 조이면 이 지표는 맞지만 다른 지표(특히 SB RFI)가 무너진다.
하나의 R 공식으로 모든 스팟을 맞출 수 없기 때문이고, 이건 근사의 구조적 한계다.

**해결책은 튜닝이 아니라 플롭 솔버다.** 실제로 플롭을 풀어 R을 측정하면 근사가 필요 없어진다.
그래서 `RealizationModel`을 인터페이스로 분리해 뒀다 — 플롭 솔버가 붙으면
`SolvedFlopRealization`을 추가하고 주입만 바꾸면 되고, 프리플롭 CFR 코드는 손대지 않는다.

### 튜닝하다 배운 것 (되돌리지 말 것)

- **R의 IP/OOP 합은 반드시 2여야 한다.** 실현 몫이 `에퀴티 × R`이고 에퀴티 합이 1이므로,
  반반일 때 팟이 정확히 나뉘려면 합이 2다. 벗어나면 팟에 없던 돈이 생긴다.
- **핸드 모양 보정은 퍼짐이 중요하다.** 0.94~1.06 안에 다 몰아넣으면 약한 오프수트도
  강한 수딧만큼 값을 챙기는 셈이라 BB가 쓰레기 패까지 콜한다.
- **상대 레인지 폭을 봐야 한다.** 포지션만 보면 SB가 무너진다. SB는 아웃오브포지션이지만
  상대(BB)가 거의 랜덤이라 잘 실현한다. 반대로 BB가 UTG의 좁은 레인지를 상대할 때는 못 챙긴다.
- **그 폭은 시작 레인지가 아니라 "따라오는 레인지"다.** 오프너의 상대는 전 레인지가 아니라
  폴드하지 않은 30~40%다. 100%로 잡으면 오프너가 과도하게 유리해져 BTN RFI가 70%까지 뛴다.

## 스트리트 확장 (턴/리버)

액션 트리는 스트리트 개수를 하드코딩하지 않는다. `GameTree`는
`streets: Street[]` 를 받아 재귀적으로 만들어지고, 지금은 `['preflop','flop']`을 넘긴다.
턴/리버 추가 = 배열에 원소 추가 + 각 스트리트의 베팅 사이즈 설정 추가.

성능이 문제지 구조가 문제가 아니게 만들어 둔다.

## Next.js를 정적으로 쓰는 법

`next.config.mjs`에 `output: 'export'`. 이러면 `next build`가 순수 HTML/JS를 뱉고
어디든 올릴 수 있다. 서비스로 갈 때는 **이 한 줄을 지우면** SSR과 `app/api/*`가 그대로 열린다.
그래서 파일 배치는 처음부터 App Router 규칙을 지킨다.

## UI 원칙 (이 프로젝트의 존재 이유)

GTO Wizard는 정확하지만 초보자에게 벽이 높다. 우리가 다르게 하는 지점:

1. **상황을 문장으로 먼저 보여준다.** "BTN vs BB SRP" 대신
   "당신은 버튼, 빅블라인드와 둘이서, 팟 5.5bb"
2. **결론을 먼저, 근거는 나중.** 매트릭스를 던지지 않고 "이 핸드는 레이즈"를 먼저 말한다.
3. **용어는 항상 옆에 뜻이 붙는다.** 3벳, C벳, 폴라라이즈 등에 인라인 설명.
4. **매트릭스는 기본이 아니라 심화 뷰.** 초보 모드에서는 접혀 있다.
5. **왜 그런지 한 줄 설명.** 빈도만 보여주고 끝내지 않는다.

정확도는 Wizard를 따라가되, 진입 장벽만 낮춘다.
